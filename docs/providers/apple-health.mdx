## Overview

Apple Health integration uses a **push-based model** where health data is sent from the user's device to Open Wearables using our mobile SDK. This is different from cloud providers like Garmin or Polar that use webhooks.

<Note>
  **Why Push-Based?** Apple HealthKit doesn't expose a cloud API. Health data lives exclusively on the user's device, so your mobile app must actively push data to your backend using our SDK.
</Note>

## Flutter SDK Quick Start

The fastest way to integrate Apple Health:

```dart
import 'package:health_bg_sync/health_bg_sync.dart';

// 1. Configure SDK
await HealthBgSync.configure();

// 2. Sign in with credentials from your backend
await HealthBgSync.signIn(
  userId: credentials.userId,
  accessToken: credentials.accessToken,
);

// 3. Request permissions
await HealthBgSync.requestAuthorization(
  types: [
    HealthDataType.steps,
    HealthDataType.heartRate,
    HealthDataType.sleep,
  ],
);

// 4. Start background sync
await HealthBgSync.startBackgroundSync();
```

## Supported Data Types

Apple Health provides the widest range of health data types:

- **Activity**: Steps, distance, flights climbed, active energy
- **Heart**: Heart rate, resting HR, HRV, VO2 max
- **Sleep**: Sleep sessions with stages (flushed to the database on every SDK sync batch; Redis only holds the in-progress accumulator until a 2-hour quiet gap closes the session)
- **Workouts**: All workout types with detailed metrics
- **Body**: Weight, height, body fat percentage, basal body temperature
- **Nutrition**: Dietary energy, protein, carbohydrates, fat, fiber, sugar, caffeine, water (→ `hydration`)
- **Women's Health**: Menstrual flow samples assembled into `/events/menstrual-cycles` (period/cycle length); cervical mucus and ovulation test results as timeseries
- **Mindfulness**: Mindful session duration as `mindful_minutes`

See the [Flutter SDK documentation](/sdk/flutter#supported-health-data-types) for the complete list of supported types.

<Note>
  Cycle-start flags (`HKMenstrualCycleStart`) are taken from the in-flight SDK payload only — timeseries rows do not store HealthKit metadata. Re-grouping across historical syncs therefore relies on a gap &gt; 1 day heuristic; rare back-to-back periods with no gap may merge until a later sync carries an explicit cycle-start flag.
</Note>

## Sleep upload integrity and recovery

The SDK sync endpoint returns `202 Accepted` when the upload is queued. This is not proof that its sleep sessions were persisted: check the completed sync status and stored sessions. Apple sleep batches are accumulated within the existing exact data source, so replaying part of a night reconciles its stored sessions instead of replacing the night with that fragment. Other devices and sources remain separate, and the existing summary priority rules choose which source to display. Sleep for one user is processed one batch at a time. When a burst of batches (such as a historical export) keeps that turn busy past the wait, the batch's other data is stored at once and its sleep moves to a separate worker task (`process_sdk_sleep`) that retries with backoff for about 25 minutes; the batch's sync status does not count that sleep, so check the stored sessions.

For old overlapping duplicate sessions, `backend/scripts/data_migrations/reconcile_apple_sleep.py` provides a manual, account-scoped dry run and an explicit `--apply` mode. Both the account and local wake-date window are required; its module docstring documents the run procedure, audit output and skipped ambiguous cases. This tool is not run at startup. Review its before snapshots and the normal database backup before an approved apply, then verify the surviving session and repeat the dry run to confirm no overlapping duplicate remains.

Before a repair pilot, finish or drain older SDK and stale-sleep worker generations: older code can still write the legacy per-user Redis state during a rolling deployment. Legacy state is saved under its recorded source identity; stages already mixed across sources cannot be separated retrospectively. Stored hypnograms are cleaned intervals rather than raw HealthKit samples, so contradictory stage labels can still require a fresh HealthKit replay. Legacy aggregate sleep not represented by its stages remains a lower bound until enough interval evidence arrives; this does not reconstruct the missing stages.

A lone shortened session cannot reveal its missing samples. Once the corrected server is deployed, Lucie's existing targeted `wearables.apple_sleep_repair` rollout can ask a compatible iPhone to replay the last 92 days of HealthKit sleep. A successful upload still requires an audit of the restored Open Wearables window, stages and duration. Historical `sleep.updated` delivery or an explicitly forced Lucie refresh must also rebuild each affected historical date; SDK `sync.completed` alone refreshes today's Lucie data. Confirm the historical sleep card before ending the repair inclusion. Replays are incremental: missing samples do not declare a deletion or an authoritative full-night replacement.

## Apple Health as a Data Bridge

Even if a provider is **not yet directly supported** by Open Wearables, its data can still be collected by syncing it into Apple Health first.

<Warning>
  **Data scope may differ.** Third-party providers often write a limited subset of their data to Apple Health compared to what's available through their native APIs. For example, a device might expose detailed HRV metrics in its own app but only sync basic heart rate samples to HealthKit. If you need the full data scope, prefer a direct provider integration when available.
</Warning>
